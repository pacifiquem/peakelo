# AGENTS.md — Working constitution for Peakelo

This file governs every agent working in this repository. It is not optional background reading —
it is the contract. If something you are about to do conflicts with this file, stop and resolve the
conflict (ask the user, or propose an edit to this file) before proceeding.

This document is living. When the user gives standing instructions during a session ("always do X",
"never do Y"), fold them back into this file in the same session rather than letting them live only
in chat history.

---

## 1. Where we are, where we're going

**Peakelo** is a chess mastering product: import games from Chess.com / Lichess, build a real
player profile from engine-backed analysis, then teach with human language (GothamChess / ChessBase
India style), drills, and a roadmap — not raw eval bars. Product intent lives in
[`docs/projectdef/coreideaflow.md`](./docs/projectdef/coreideaflow.md). Sample human analysis that
the product should feel like lives in [`docs/projectdef/sample-bare-analysis/`](./docs/projectdef/sample-bare-analysis/).

**Shipped today:** monorepo scaffold only. No product APIs, no ingest, no payments. Do not invent
UI or routes that pretend analysis, auth, or billing already exist.

The mission from here: a **fully functional, production-grade, fast** analysis and training site,
built by agents held to professional engineering standards. Every backend change is unfinished
until the frontend actually calls it. Functional does **not** mean it is allowed to look worse
than the design system in [`docs/design/ui.md`](./docs/design/ui.md).

Treat code generated by external tools or templates with the same suspicion you would apply to an
unreviewed third-party dependency. Skim generated config before running install/lint/build hooks.

## 2. Prime directives (non-negotiable)

These override convenience, speed of typing, or "I think this is probably fine."

1. **Stop and ask when unsure.** Ambiguous requirements, hard-to-reverse decisions (schema, auth,
   a new paid vendor, deleting data, changing a public contract), or two reasonable approaches
   with no clear winner — stop and ask. A wrong foundational decision is slower than a question.
2. **No dummy data, no fake delays, no simulated state — anywhere.** Hardcoded arrays, fake
   `setTimeout` success, and "pretend this worked" flows must become real API calls with real
   loading / error / empty / success states, styled to the design system. A throwaway spike is
   allowed only when the user explicitly asks for `/prototype`.
3. **Backend work is not done until it is integrated — visually as well as functionally.** A route
   with no consumer, a UI still on mock data "for now", or real data behind an unstyled spinner is
   the same failure: unfinished work.
4. **Production-grade, not prototype-grade.** Input validation, error handling, auth checks, rate
   limits, structured logs, no secrets in code. See §10.
5. **No scaffolding or weak stand-ins for core product behavior.** Do not ship regex-as-intelligence,
   keyword "extractors", paste-only facades, or modules that only prove tables exist — especially
   for analysis, player profiling, or payments. If the honest implementation needs a model, a
   vendor, a design choice, or more time than the turn allows: stop and ask.
6. **Reuse relentlessly.** Before writing a function, type, client, hook, or schema, search for an
   existing one. Three similar lines is fine; a third copy of the same 20-line block is not.
   Apply the `codebase-design` skill: small interfaces, real implementation behind them.
7. **Minimal comments.** Default to zero. Only write a comment that captures a non-obvious *why*.
8. **Test what you build.** Use the `tdd` skill where it applies. Every API route has a contract
   test. Every non-trivial function is tested at its public seam. Typecheck + lint + tests before
   calling a task done.
9. **Self-verify with MCP tools.** Unit tests are necessary, not sufficient. For user-visible or
   multi-step behavior, drive the real path (Playwright MCP for UI). Do not mark work done until
   that pass succeeds or the user accepts residual risk in writing.
10. **Keep `TODO.md` and `ENV.md` current** as part of the task, not after.
11. **Never fabricate success.** If you did not verify it, say so.
12. **Never commit, push, or merge without explicit user approval after review.** Implementing
    files is fine. When a slice is ready, show the diff and ask. Prior-session approval does not
    carry forward.
13. **UI redesign ≠ functionality change.** Visual work must not change APIs, routes, schemas,
    auth, or analysis logic unless the user explicitly asks.
14. **pnpm only.** Never run `npm` or `yarn` in this repo. Root `preinstall` blocks them. New
    packages are added with `pnpm add` / `pnpm add -D` from the relevant filter.

## 3. Repository layout

```
/
├── AGENTS.md
├── ENV.md
├── TODO.md
├── docs/projectdef/          ← product intent + sample analyses
├── docs/design/              ← visual system + AlignUI usage
├── client/                   ← @peakelo/client — Next.js App Router + AlignUI
├── server/                   ← @peakelo/server — Fastify + SWC + Vitest
│   ├── src/app.ts, index.ts
│   ├── src/config/env.ts
│   ├── src/lib/              ← logger, cors helpers
│   ├── src/common/           ← errors, error-handler
│   ├── src/routes/           ← process-level routes only (health)
│   ├── src/modules/          ← domain modules as they are built
│   └── prisma/               ← schema placeholder until the first model
├── packages/shared/          ← @peakelo/shared — Zod / DTOs / enums / constants (§3.1)
├── packages/engine/          ← @peakelo/engine — pure chess rules, Node + browser (§3.2)
└── .agents/skills/           ← project skills (align-ui, tdd, …)
```

Workspace packages: `client/`, `server/`, `packages/*`. Build order: `@peakelo/shared` then
`@peakelo/engine` then server then client. Domain HTTP modules belong under
`server/src/modules/` — do not pile product handlers into `routes/`. Routes stay thin.

### 3.1 `@peakelo/shared` — what goes in

Same job as script-ai's `packages/shared`: **one Zod schema is the type** for anything that
crosses the client/server boundary. If both sides would otherwise copy a shape, it lives here.

**Put here (and only here):**

| Kind | Examples for Peakelo |
| --- | --- |
| Request / query / body schemas | signup, import-N-games, start analysis |
| Public response DTOs | `PublicUser`, `PublicGame`, `PublicPlayerProfile`, analysis writeup payload |
| Zod enums | `timeControl` (`bullet` \| `blitz` \| `rapid`), `gameSource` (`chesscom` \| `lichess`), `plan` (`analysis` \| `training`) |
| Cross-cutting constants | page size, plan prices (`14.99` / `34.99` / `1.22`), cookie names, header names |
| Pagination + API error envelope | already in `api-error.ts`, `pagination.ts` |

Pattern: `export const fooSchema = z.object({...}); export type Foo = z.infer<typeof fooSchema>;`

**Do not put here:**

- Fastify, Prisma, Next, React, Pino, env loading
- Secrets, HTTP clients, file I/O
- Move generation, FEN/PGN parsers, legal-move logic → `@peakelo/engine`
- Stockfish process / WASM loader → `server/` or `client/` adapter
- AlignUI components, CSS, hooks
- Server-only crypto (password hash, JWT sign)

Do not add a domain file until that API exists. Empty speculative DTO files are forbidden (§2.5).
When a route lands, its Zod contract lands in `packages/shared/src/<domain>.ts` in the same change.

### 3.2 `@peakelo/engine` — library, not an app

`@peakelo/engine` is imported by **both** `@peakelo/client` and `@peakelo/server`. It is not a
gateway, worker, or root-level app. No process, no port, no `child_process`.

**Put here:** pure functions that run in Node and the browser — squares, FEN/PGN/SAN/UCI, legal
moves, apply-move, clock arithmetic.

**Do not put here:** Stockfish binary, WASM bootstrap, HTTP, Prisma, React, filesystem, fetch.

Adapters (spawn Stockfish on the server, or load WASM in the browser) live next to the caller.
They consume this package for positions; they do not live inside it.

## 4. Technology baseline

Treat these as the default path. If one is wrong for a specific requirement, **stop and confirm**
rather than silently deviate, then update this section.

- **Language:** TypeScript everywhere. No `any` unless justified inline.
- **Package manager / workspaces:** pnpm. No Turborepo/Nx until build time is a bottleneck.
- **Frontend:** Next.js App Router in `client/`. **AlignUI** (copy-paste components, Tailwind v4,
  Remix Icon). Visual language: polished neo-brutalism with restrained vaporwave / Y2K — see
  `docs/design/ui.md`. Mandatory skill: `align-ui`.
- **Backend:** Node.js + **Fastify**. **SWC** transpiles (`@swc/cli`, `@swc-node/register`); `tsc`
  only type-checks.
- **Database (planned):** Postgres + **Prisma**. `DATABASE_URL` (pooled) vs `DIRECT_URL` (migrate).
  Do not add the first model without asking.
- **Validation:** **Zod** for request bodies, env, and config. One schema, not a schema plus a
  hand-written type. Shared schemas live in `@peakelo/shared` (§3.1).
- **Logging:** **Pino** on the server. No `console.log` in server code.
- **Testing:** **Vitest** on server, shared, and engine.
- **Formatting & linting:** Prettier at the root; ESLint per package with `eslint-config-prettier`.
- **Chess rules:** `@peakelo/engine` (§3.2). Do not add a Stockfish adapter without asking.

If a task needs a technology not listed here (new SaaS, new datastore, paid API), stop and ask,
then add it here once decided.

## 5. Performance

Speed is a first-class requirement, not a follow-up pass. Apply the technique that fits the layer:

- Index every column used in `WHERE` / `ORDER BY` / join in the same migration as the query.
- Paginate list endpoints. Never return an unbounded array.
- Avoid N+1. One Prisma client per process.
- No ad hoc `prisma.$queryRaw` from `server/src/modules/**`. Raw SQL lives in `src/db/` only.
- Push slow work (engine analysis, embeddings, imports) into background jobs once that seam exists.
- Validate and reject bad input before any DB / engine / model work.
- Frontend: route-level splitting, request cache/dedupe, virtualize long game lists.

Do not add caching or job queues for paths that are not actually slow.

## 6. Multi-agent delivery

For non-trivial work (new module, multi-file feature, schema change), the orchestrating agent must:

1. Spawn implementer subagent(s) for bounded slices.
2. Always spawn one strict reviewer. The reviewer assumes the deliverable is wrong and must
   falsify claims of correctness.
3. Feed findings back until the reviewer cannot prove remaining material defects, or the user
   accepts residual risk in writing.

### Skills to reach for

| Situation | Skill |
| --- | --- |
| Nontrivial implementation from a spec | `implement` |
| New logic, test-first | `tdd` |
| Module interface / seam / repetition | `codebase-design` |
| Term, entity, or ADR | `domain-modeling` |
| Fastify routes, middleware, errors, DB | `nodejs-backend-patterns` |
| Any `client/` UI | `align-ui` then `frontend-design` |
| Next.js / React performance | `vercel-react-best-practices` |
| Auth, input, secrets, OWASP | `security-and-hardening` |
| Before calling a change done | `code-review` |
| Hard bug | `diagnosing-bugs` |
| Discover another skill | `find-skills` |

Default loop: read `ENV.md` + `TODO.md` → confirm scope → implement (TDD where it fits) →
typecheck + lint + test → review → verify the real flow → update ledgers.

For UI: read `align-ui` and `docs/design/ui.md` **before** the first component. Never ship
`window.alert` / `confirm` / `prompt` or naked red error text as the only feedback.

Every process environment variable is listed in `ENV.md` with purpose, required/optional, and

is unfinished work. Do not invent undocumented env.

Prefer MCP tools over raw CLI against the same system (GitHub, browser, DB). If no MCP exists for

### 8.1 Playwright screenshots and traces

All Playwright-captured images (and related traces/snapshots you choose to keep) go in
**`tmp/playwright/`**. Never write a screenshot to the repo root or any other package folder.

Rules:

1. Pass a path under `tmp/playwright/` every time you take a screenshot
   (example: `tmp/playwright/join-desktop.png`).
2. `tmp/playwright/` is gitignored. Do not force-add it.
3. **At the start of every session**, before the first screenshot: delete the folder contents and
   recreate it (`rm -rf tmp/playwright && mkdir -p tmp/playwright`).
4. `.playwright-mcp/` is also gitignored (MCP internals). Do not commit it.

## 9. Coding standards

- Shared types between client and server belong in `@peakelo/shared` (§3.1). Chess rules belong
  in `@peakelo/engine` (§3.2).
- Deep modules, thin routes.
- Errors are typed and handled in `server/src/common/error-handler.ts`. No `throw "string"`.
- No secrets in code.
- Naming: `PascalCase` components/classes, `camelCase` functions/variables/hooks.
- No speculative abstraction.

---

## 10. Production-readiness checklist

Apply before calling backend work done:

- Input validated at the boundary (Zod).
- Auth + tenancy on every route that touches user data (once those exist).
- Errors return `{ error: { code, message, details? } }` — no stack traces to clients.
- Rate limiting on public and auth-sensitive routes.
- Structured logs on request lifecycle and errors.
- Long-running analysis is not on the request cycle once jobs exist.
- Health: `/health` liveness, `/health/ready` for dependencies.
- Graceful shutdown closes the server (and later DB/queue).
- No silent `TODO`/`FIXME` in shipped code — it goes in `TODO.md` or gets done.
- Tests + a real-flow verify.

## 11. `TODO.md` contract

`TODO.md` is the ledger for what is done, in flight, and not started. Update it as part of the
task. Move an item to Done only once it passes §10.

After a session that implements or defers work, end the user-facing message with:

1. At most three lines of project state, including rough percentages.
2. A **Done** table for this session only.
3. **Pending** / **Skipped** tables when anything in scope is still open.

Categories do not overlap.

## 12. When to stop and ask

- Product intent in `docs/projectdef/` is underspecified for the task.
- New paid vendor, datastore, or engine protocol.
- Destructive or hard-to-reverse change (schema drop, force-push).
- Two implementations that materially affect future work.
- The "implementation" would be scaffolding or weak intelligence.
- About to `git commit` / `git push` / open or merge a PR.
- This file conflicts with an explicit user instruction in the moment.
